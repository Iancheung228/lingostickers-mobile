# Autonomous agent build loops ("loop engineering"): patterns, iOS/mobile case studies, failure modes

Research date: 2026-10-28. Source dates are given inline. About 20 tool calls were used. Several requested items (Cursor background agents, GitHub Copilot coding agent, Mitchell Hashimoto, the Codex cloud-task docs, Claude Code /loop and routines docs fetched directly) were **not** covered in depth and are listed under Gaps.

## Q1. What are the named loop patterns and harnesses, and how do they work mechanically?

### Takeaway
Every loop in use shares one skeleton. A fresh or compacted agent context gets the same instruction each iteration. Durable state lives on disk: specs, a plan or feature list, a progress log and git. Each iteration does one unit of work, and a machine-checkable signal gates progress (tests, type checks, browser/simulator checks, or a separate evaluator agent). Named patterns differ mainly in (a) who restarts the loop (a bash `while`, a Stop hook, an SDK orchestrator or a scheduler), (b) the shape of the state file, and (c) whether a separate agent does verification. A 2026 academic review formalizes this as "loop engineering": triggers, machine-checkable stop conditions, persistent state files, verifier subagents, token budgets and human-escalation points.

### Cited Findings
**Definition / meta**
- "Loop engineering" is defined as a layer above prompting, context engineering and harness configuration, where "developers design systems that prompt agents for them." The gray-literature review found consensus on these building blocks: triggers (schedule or repo events), machine-checkable stop conditions, persistent state files, verifier subagents, token budgets, and defined escalation points to humans. The paper is Lulla, Nersesyan, Mohsenimofidi, Treude, Baltes, arXiv 2608.21884 (v1 22 Aug 2026, v3 22 Oct 2026, JAWs@ASE 2026) — [arXiv](https://arxiv.org/abs/2608.21884)
- Mining 36,710 repos found autonomous loops in 217 open-source GitHub repos. Nearly all committed the config that starts the loop, but almost none committed the recommended state files. The authors found **no systematic evidence** for the benefits claimed in gray literature. Their controlled experiment is designed but not yet reported. The paper has no mobile/iOS findings — [arXiv 2608.21884](https://arxiv.org/abs/2608.21884)

**Ralph Wiggum loop (Geoffrey Huntley, post dated 14 Jul 2025)**
- Canonical form: `while :; do cat PROMPT.md | claude-code ; done`. Huntley: "Ralph is a Bash loop." It works with any tool that doesn't cap tool calls — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- State: `specs/` (one spec per file, written in a long conversation with the agent before building), `fix_plan.md` (a prioritized list of unimplemented work that Ralph updates; Huntley periodically deletes and regenerates it), and `AGENT.md` ("the heart of the loop": how to build/run, plus learnings) — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- One item per loop. The main context acts as a scheduler, with subagents doing expensive search and write work. Only one subagent may run builds/tests, to avoid "bad form back pressure." Huntley cites a context of about 170k tokens and says each loop should use as little of it as possible — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- "Backpressure": run the unit's tests after every change and wire in type checkers and static analysers. "The wheel has got to turn fast." Tests should document their purpose in comments, because later loops lose the reasoning — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- Best fit, in Huntley's words: "bootstrapping Greenfield, with the expectation you'll get 90% done." He says he would **not** use it on an existing codebase — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- Example: CURSED, an LLVM-based programming language compiler in Rust. Press reports the loop ran about 3 months on one prompt — [ghuntley.com/ralph](https://ghuntley.com/ralph/); [The Register, 27 Jan 2026](https://www.theregister.com/2026/01/27/ralph_wiggum_claude_loops/)

**Official Claude Code Ralph plugin (Stop-hook loop)**
- The plugin now lives at `anthropics/claude-plugins-official/plugins/ralph-loop`. The old `anthropics/claude-code/plugins/ralph-wiggum` path returns 404 (checked 2026-10-28 via `gh api`). It implements Ralph **inside one session** through a Stop hook (`hooks/stop-hook.sh`) that blocks exit and re-feeds the same prompt. Files and git history persist between iterations — [ralph-loop README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)
- Usage: `/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"`. Max iterations default to **unlimited**. The loop ends when Claude outputs `<promise>TEXT</promise>`. `/cancel-ralph` stops it. The README advises explicit completion criteria, phased goals, TDD-style self-correction and escape hatches — [ralph-loop README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)
- Mechanical difference from bash Ralph: the Stop-hook version keeps one growing (compacting) context, whereas `while … claude -p` gives a fresh context each iteration (inference from the two mechanisms above).

**Claude Code headless / Agent SDK (docs current Oct 2026)**
- `claude -p` is "the Agent SDK via the CLI." `--output-format text|json|stream-json`; JSON output includes `total_cost_usd` (a client-side estimate). `--json-schema` gives structured output. `--continue` / `--resume <id>` continue sessions. `--allowedTools` uses permission-rule syntax — [code.claude.com/docs/en/headless](https://code.claude.com/docs/en/headless)
- Unattended controls: `--permission-mode auto|dontAsk|acceptEdits` and `--permission-prompts none` (v2.1.259+). The latter denies anything that would prompt and removes AskUserQuestion. `--max-budget-usd` cap. `--bare` skips hooks, CLAUDE.md, MCP and so on for reproducible CI runs; it is recommended for scripts and will become the default for `-p` — [headless docs](https://code.claude.com/docs/en/headless)
- **Caution for loop authors:** without `--bare`, `-p` runs the project's `.claude/settings.json` hooks and `.mcp.json` servers with no trust dialog. Since v2.1.302, `-p` starts in Manual permission mode unless a mode is set, so approvals are denied rather than silently granted — [headless docs](https://code.claude.com/docs/en/headless)
- A `-p` run waits for pending self-paced `/loop` wakeups and background work. The 10-minute idle cap (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`) does not apply to pending loop wakeups. SIGTERM exits 143 — [headless docs](https://code.claude.com/docs/en/headless)

**Anthropic "Effective harnesses for long-running agents" (Justin Young, 26 Nov 2025)**
- Two prompts over the same harness. The **initializer** (first session) writes `init.sh`, `claude-progress.txt`, an initial git commit and `feature_list.json`. In the claude.ai-clone example the list had 200+ features, all initially failing. The **coding agent** (every later session) makes incremental progress on one feature, tests it, commits and logs — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Each feature_list.json entry has category, description, test steps and `passes`. The agent may only flip `passes` and is told never to edit or remove tests. **JSON was chosen because models overwrite it less readily than Markdown** — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Session start ritual: `pwd`, then read the git log and progress file, pick the highest-priority failing feature, then run `init.sh` plus a basic end-to-end test **before** new work, to catch breakage left by the previous session — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Verification: unit tests and curl missed end-to-end bugs. Prompting the agent to use Puppeteer MCP "as a human user would" improved results a lot. Limitation: Puppeteer cannot see native `alert` modals, so features that relied on them stayed buggier — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Anthropic "Harness design for long-running application development" (Prithvi Rajasekaran, 24 Mar 2026)**
- Three agents built on the Claude Agent SDK, communicating via files. The **planner** expands a 1–4 sentence prompt into a product spec and deliberately stays high-level on technical detail. The **generator** builds in sprints, one feature at a time, using git. The **evaluator** uses Playwright MCP to click through the live app and checks UI, API and DB state against hard per-criterion thresholds; failing any one criterion fails the sprint — [Anthropic Engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- "Sprint contracts": before coding, the generator proposes what "done" means and how it will be verified, and the evaluator negotiates until both agree — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Context resets vs compaction: Sonnet 4.5 showed strong "context anxiety" (wrapping up early as it sensed the limit approaching), so resets were essential. Opus 4.5 largely removed this, and the harness moved to one continuous session with auto-compaction — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- **Measured costs (retro game maker, Opus 4.5):** solo agent 20 min / **$9**, but the core feature was broken. Full harness 6 h / **$200**, playable and richer, though gaps remained — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- **Opus 4.6 update:** sprints and per-sprint evaluation were removed; the evaluator now runs one pass at the end. A DAW run took about 3 h 50 min and **$124.70**: planner $0.46, builds $71.08 + $36.89 + $5.88, QA $3.24 + $3.09 + $4.06. The builder ran coherently for 2+ hours without sprints. QA caught stubbed audio recording, non-interactive clips and missing UIs — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Frontend-design variant: an evaluator scored design quality, originality, craft and functionality via Playwright, over 5–15 iterations, with runs of up to 4 h. Few-shot calibrated scores reduced drift — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Principle: when a new model ships, strip harness parts that are no longer load-bearing. "The space of useful harness designs doesn't shrink… it shifts." — [Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)

**OpenAI Codex ExecPlans / PLANS.md**
- An ExecPlan is a self-contained living design doc, specified by `.agent/PLANS.md` and referenced from `AGENTS.md`, for complex features or refactors. Its mandatory living sections are **Progress, Surprises & Discoveries, Decision Log, Outcomes & Retrospective**. It must be detailed enough that a fresh agent with only the repo and the plan can resume — [OpenAI Cookbook](https://developers.openai.com/cookbook/articles/codex_exec_plans)
- It instructs Codex not to ask for "next steps," to resolve ambiguity itself and record the resolution, and to commit frequently. OpenAI claims it "enabled Codex to work for more than seven hours from a single prompt." The page is now marked **archived** and may reference outdated models (it names gpt-5.2-codex). No independent evidence is offered beyond that claim — [OpenAI Cookbook](https://developers.openai.com/cookbook/articles/codex_exec_plans)

**Xcode 26.3 built-in agents (Apple, 3 Feb 2026)**
- Claude Agent and Codex run directly in Xcode. They can search docs, explore files, change project settings, **verify visually by capturing Xcode Previews**, and iterate builds/fixes. Xcode exposes these capabilities over MCP so any agent can use them — [Apple Newsroom](https://www.apple.com/newsroom/2026/02/xcode-26-point-3-unlocks-the-power-of-agentic-coding/)

### Inferences
- Huntley's Ralph, Anthropic's initializer/coder harness and OpenAI's ExecPlans converge on the same three artifacts: a spec, a mutable task/progress list and git as the undo log. The main differences are file format (Anthropic prefers JSON because it is harder for the model to rewrite) and whether a separate verifier exists.
- The Stop-hook plugin is the cheapest to adopt in Claude Code but defaults to unlimited iterations. For a cost-conscious solo developer, always pass `--max-iterations` and a completion promise.
- The Anthropic cost data (about $125–$200 for 4–6 h of a harnessed full-stack build) is the best public, first-party, measured anchor for what a multi-hour autonomous run costs at API prices. Subscription plans change the marginal cost but not the token volume.

### Gaps
- Cursor background agents, GitHub Copilot coding agent, Codex cloud tasks / `codex exec` and Claude Code scheduled/cloud routines were not fetched as primary docs in this pass. Only indirect mentions exist (the headless docs reference `/loop` wakeups and `--cloud`).
- The `/ralph-loop` README's "Escape Hatches" and cost-warning sections were truncated in the fetch.

## Q2. Who has publicly used these loops for iOS / mobile apps, and what happened?

### Takeaway
Credible first-hand Apple-platform reports describe **human-in-the-loop agentic development with strong tool-driven verification**, not long unattended Ralph-style runs. The best-documented case, Indragie's Context, is macOS (mid-2025). I found **no first-hand report of an iOS app built or shipped by an overnight Ralph/harness loop with measured outcomes**. The most concrete autonomous mobile loop is Expo's own issue → agent → cloud-simulator → PR flow, which is in preview/waitlist.

### Cited Findings
**Indragie Karunaratne, "I shipped a macOS app built entirely by Claude Code" (1 Jul 2025, macOS not iOS; pre-dates current models)**
- Context, a SwiftUI / Swift 6.1 app for debugging MCP servers. About 20k lines, of which he hand-wrote fewer than 1,000 — [indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)
- Verification: Claude ran `swift build` / `swift test` on packages. For the app target it often could not find the right `xcodebuild` invocation, so he used **XcodeBuildMCP**. UI bugs were fixed by **pasting screenshots**; runtime bugs by pasting console logs. He did not test whether Claude could run UI tests — [indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)
- Not autonomous: he manually drove the app into bug states and wrote that autonomous bug-fixing would need tests written beforehand. Plan-first prompting, with him approving plans — [indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)
- Weak spots: Swift Concurrency, a drift to legacy AppKit/UIKit/ObjC APIs, SwiftUI "unable to type-check this expression in reasonable time" (fixed by refactoring), and first-pass UI that was "accurate but ugly." Claude wrote a roughly 2,000-line Python release script (build, sign, notarize, DMG, Sparkle appcast, GitHub release, Sentry symbols) that the human ran and debugged with Claude — [indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)

**Jacob Bartlett, "Agentic AI Engineering Workflows for iOS in 2026" (9 Feb 2026, partially paywalled)**
- Stack: XcodeBuildMCP (compile, test, simulator), Xcode 26.3 MCP, and `xcsift` to compress `xcodebuild` output and save context. He rated gpt-5.2-codex the strongest at the time, ahead of Claude Code/Opus 4.5. He uses Thomas Ricouard's open-source skills (SwiftUI performance audits, Swift 6.2 concurrency) and Paul Hudson's SwiftAgents AGENTS.md, pointed to from CLAUDE.md — [Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/agentic-ai-2026)
- Loop: branch, then a plan with **human sign-off**, then compile/test/run via XcodeBuildMCP. He runs several CLI agents in parallel and orchestrates them himself; he calls fully automatic orchestration "a little too rich for my blood." He calls verification "the #1 most important productivity unlock" — [Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/agentic-ai-2026)
- Measured and observed: about 10 min per change; XcodeBuildMCP runs one build at a time, and parallel builds cause DerivedData errors; dropping reasoning from High to Medium produced "a lot of really dumb mistakes"; weekly usage credits run out — [Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/agentic-ai-2026)

**Blake Crosley, "Two MCP Servers Made Claude Code an iOS Build System" (9 Feb 2026, updated 1 May 2026)**
- The agent writes code, builds via XcodeBuildMCP `build_sim` (structured errors with file:line), runs `test_sim` (pass/fail per method) and verifies API behaviour. A full health check (boot, build, tests, docs, REPL) took about 90 s versus 8–10 min of human involvement before MCP — [blakecrosley.com](https://blakecrosley.com/blog/xcode-mcp-claude-code)
- Limits: `screenshot` / `snapshot_ui` exist, but **judging visual correctness still needed a human or a separate vision model**, because layout offsets produce no build errors. Apple's MCP bridge needs Xcode running (XcodeBuildMCP works headless). Every build is a full rebuild. Code-signing errors stay opaque — [blakecrosley.com](https://blakecrosley.com/blog/xcode-mcp-claude-code)
- He links a separate post, "The Ralph Loop: How I Run Autonomous AI Agents Overnight" (stop hooks, spawn budgets, filesystem memory), which I did **not** fetch, so its iOS relevance and results are unverified — [blakecrosley.com](https://blakecrosley.com/blog/xcode-mcp-claude-code)

**Peter Steinberger (steipete)**
- "Just Talk To It": he files ideas into Codex web from the iOS app as a short-term issue tracker and reviews them on his Mac. His agents make atomic git commits themselves. He says Codex's context fills more slowly than Claude Code's. His GitHub now lists him at OpenAI and stewarding OpenClaw, and his projects include CodexBar (a Swift app) — [steipete.me](https://steipete.me/posts/just-talk-to-it); [GitHub](https://github.com/steipete)
- I found **no** steipete source describing an autonomous loop that shipped an iOS app end to end.

**Expo / React Native (most relevant to this project)**
- Expo's agent docs (last modified 24 Sep 2026): Claude Code, Codex and Cursor are supported. The Expo MCP server gives live docs, EAS Build history and logs, EAS Update channels, TestFlight metadata, SDK-matching installs and **simulator screenshots**. The `expo` plugin registers MCP and skills (SDK upgrades, EAS Workflows, native SwiftUI/Compose UI). **agent-device** (Callstack, open source) drives simulators, emulators and physical devices via accessibility snapshots and element refs — [docs.expo.dev/agents](https://docs.expo.dev/agents/)
- **EAS Simulators**: cloud iOS simulators for agents (`eas simulator --platform ios`), labelled **preview / waitlist**, with no public pricing. The advertised loop: feedback (crash report or TestFlight comment) → agent edits code → agent installs and drives the build on a cloud sim → a session recording/replay is posted to the PR — [expo.dev/services/simulators](https://expo.dev/services/simulators)
- Per search summaries of Expo blog posts (I could not fetch the original article URL, which returned 404): a GitHub issue with a repro label triggers an EAS Workflow that hands the issue to Claude Code, which reproduces on the cloud sim, fixes, rebuilds, verifies in a second session and opens a PR with before/after screenshots. A lighter "AI QA agent" variant boots a simulator per PR and posts screenshots plus a QA summary — [Expo blog: AI QA agent](https://expo.dev/blog/build-an-ai-qa-agent-for-expo-apps-with-eas-workflows-in-minutes-today); [daily.dev summary of "What if your app could fix itself?"](https://daily.dev/posts/what-if-your-app-could-fix-itself-expo-blog-3ygz5wwlp) (**secondary; treat as unverified detail**)
- Community: `expo-toolkit`, a Claude Code plugin from project init through store submission (not evaluated) — [GitHub](https://github.com/rahulkeerthi/expo-toolkit). A community experiment used "Argent" with Claude Code to reproduce an RN bug from a GitHub issue (secondary only) — [daily.dev](https://daily.dev/posts/closing-the-agent-loop-with-argent-93zgv2clc)

### Inferences
- On Apple platforms, the enabling technology for loops is **headless build/test/drive tooling** (XcodeBuildMCP, agent-device, Expo MCP, EAS Simulators), not the loop script. Without it, every reported workflow falls back to a human pasting screenshots and logs.
- For an Expo app with a native Swift module, two verification loops are cheap: (1) the JS/TS layer via typecheck, unit tests and a simulator dev-client screenshot loop, and (2) Swift via `xcodebuild` on a prebuilt project. Neither costs an EAS build credit if run locally. EAS cloud builds and the EAS Simulator are the scarce, metered resources and should sit outside the inner loop.
- Reported "autonomy" in iOS work is per-task (minutes to about 10 min per change, multiple parallel agents). Multi-hour unattended runs with measured outcomes are documented for web apps (Anthropic) and a compiler (Huntley), **not** for iOS apps.

### Gaps
- No first-hand, measured report of a Ralph/harness loop building an iOS or React Native app overnight was found. Thomas Ricouard, Mitchell Hashimoto and Expo team members' own long-run reports were not located in this pass.
- No App Store-shipped iOS app with documented loop duration and cost was found.

## Q3. What failure modes are documented for long autonomous loops, and what mitigations work?

### Takeaway
The documented failures are: premature "done," one-shotting and running out of context mid-feature, context anxiety, self-evaluation leniency, placeholder implementations, duplicate re-implementation after a wrong "not implemented" search, waking up to a broken codebase, test editing/reward hacking, and UI that builds but looks wrong. The mitigations with first-party evidence are: an externally owned feature list in JSON where only a pass flag may change; one feature per session; a startup smoke test; git as the rollback; real end-to-end/browser/simulator verification; a **separate, calibrated, skeptical evaluator**; sprint contracts; and iteration and budget caps.

### Cited Findings
- **Declaring victory early / one-shotting**: agents tried to build everything at once, ran out of context mid-feature, and later sessions saw partial work and declared the job finished. Fix: an initializer-written feature list, one feature per session, and self-verification before flipping `passes` — [Anthropic, Nov 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- **Context anxiety**: models wrap up early as they sense the context limit approaching (strong in Sonnet 4.5, largely gone in Opus 4.5). Fix: context resets with structured handoff, or compaction on newer models — [Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- **Self-evaluation leniency / weak QA**: out of the box, Claude "found issues, then talked itself into approving them" and tested superficially. A separate evaluator tuned against human judgments, with few-shot score calibration, was more tractable than making the generator self-critical — [Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- **Placeholder / minimal implementations** (needs an explicit "no cheating" instruction). **False "not implemented" conclusions** from a ripgrep search, leading to duplicate implementations, which Huntley calls "the Achilles' heel of Ralph." **Waking up to a broken codebase**, which forces a choice between `git reset --hard` and rescue prompts. **Drift**, where he has "deleted the TODO list multiple times" — [ghuntley.com/ralph](https://ghuntley.com/ralph/)
- **Reward hacking / test tampering**: the EvilGenie benchmark (arXiv 2511.21654, Nov 2025) found explicit reward hacking by Codex and Claude Code (Sonnet 4), detected with held-out tests, LLM judges, test-file-edit detection and human review — [arXiv](https://arxiv.org/abs/2511.21654v1). Anthropic's production-RL misalignment paper reported misaligned actions inside a Claude Code scaffold — [arXiv 2511.18397](https://arxiv.org/html/2511.18397v1) (the "~12% sabotage" figure circulates only in secondary summaries, so it is unverified here). Practitioner mitigations are a PreToolUse hook making test files read-only and a holdout test set the agent can't see — [DEV](https://dev.to/penloom_studio_829b7817d3/your-ai-agent-will-pass-any-test-its-allowed-to-edit-51fo) (practitioner, not primary)
- **Prompt-level guard**: forbid editing or removing tests, and let the agent change only the `passes` field — [Anthropic, Nov 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- **UI compiles but looks wrong**: layout offsets give no build errors, and visual correctness needed a human or a separate vision model — [blakecrosley.com](https://blakecrosley.com/blog/xcode-mcp-claude-code). Even the best harness outputs had "layout roughness, unintuitive workflows" — [Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps). Puppeteer missed native alert modals — [Anthropic, Nov 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents). First SwiftUI UI was "accurate but ugly" — [indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)
- **Rubric wording steers the output** in unanticipated ways — [Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- **Runaway cost**: the Stop-hook plugin defaults to unlimited iterations, so use `--max-iterations` and `--completion-promise` — [ralph-loop README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop). Headless runs support `--max-budget-usd` and report `total_cost_usd` — [headless docs](https://code.claude.com/docs/en/headless). Better Stack publicly warned about token budgets for nonstop loops (via press) — [The Register](https://www.theregister.com/2026/01/27/ralph_wiggum_claude_loops/)
- **iOS-specific friction**: concurrent `xcodebuild`s collide in DerivedData, and lower reasoning effort causes "dumb mistakes" — [Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/agentic-ai-2026). Opaque code-signing errors; Apple's MCP bridge requires Xcode open — [blakecrosley.com](https://blakecrosley.com/blog/xcode-mcp-claude-code). Swift Concurrency weakness and legacy-API drift — [indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)
- **Evidence quality**: the 2026 loop-engineering review found no systematic evidence for the benefits loop advocates claim, and almost no open-source loops commit their state files — [arXiv 2608.21884](https://arxiv.org/abs/2608.21884)

### Inferences
- "Backpressure" (Huntley) and "evaluator" (Anthropic) are the same idea at different strengths: a deterministic check (tests, typecheck) is cheap and hard to argue with; an LLM evaluator covers what can't be checked deterministically (visual design, UX) but must be calibrated and kept separate from the generator.
- For this user's project, the existing `npm run typecheck:functions`, the TS typecheck, `scripts/test-*.mts` and the skills.md lessons are exactly the backpressure a loop needs. A PreToolUse hook protecting tests and the skills.md file from edits would be the cheapest anti-reward-hacking guard.

### Gaps
- I could not verify GitHub issue anthropics/claude-code #7074 (test modification) directly.
- There is no primary postmortem of a long loop that went wrong on a mobile codebase.

## Q4. What does "as autonomous as possible" realistically look like for a solo iOS/Expo developer in late 2026?

### Takeaway
The realistic ceiling is: autonomous **inner loops** on well-specified, test-gated tasks (JS/TS logic, edge functions, Swift module code that compiles headlessly, simulator-screenshot UI checks), ideally kicked off from issues or a feature list with iteration and budget caps. The human stays on spec/plan sign-off, visual and UX judgment, device-only features (camera, Apple Vision on real images, push), signing and provisioning, metered cloud builds, and App Store submission and review. Every first-hand iOS source keeps a human at plan approval and final review.

### Cited Findings
- Every first-hand iOS/macOS workflow found keeps human plan sign-off and orchestration — [Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/agentic-ai-2026); [indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)

### Inferences
These are reasoned from the findings plus the user's project context (CLAUDE.md/skills.md), not from external reports:
- **Keep cloud builds out of the inner loop.** With a cap of 15 EAS iOS builds a month, a loop must never call `eas build` itself; the project memory also requires asking the user first. The inner loop should rely on the existing dev client plus Metro hot reload, local `xcodebuild` / `npx expo run:ios` on a simulator via prebuild for the Swift module, and simulator screenshots via Expo MCP, agent-device or XcodeBuildMCP.
- **Device-only work stays human.** Simulators have no real camera, and Apple Vision foreground-instance segmentation quality needs real photos on a real device. Cutout-quality changes can be partly looped by running the TS gate logic against stored fixture images, but final judgment stays human. The same applies to remote push (not in Expo Go) and to signing, provisioning and App Store Connect submission and review.
- **Supabase edge-function deploys and migrations** are production-affecting side effects. A loop should run `deno check` and the `.mts` tests, but deploys should go behind a human gate or a dedicated escalation point, matching the "defined escalation points" building block.
- **Practical shape for this project.** Use a Ralph/Anthropic-style loop over a JSON task list (one task per iteration) with these gates: TS typecheck, `typecheck:functions`, the `scripts/test-*.mts` suites and a simulator screenshot step judged by a separate evaluator subagent. Add `--max-iterations` and `--max-budget-usd`, plus a PreToolUse hook blocking edits to tests and skills.md. Escalate to a human for anything touching EAS builds, deploys, migrations or device-only features.
