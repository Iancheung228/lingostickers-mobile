# Build the verifier first, then the loop

People who use loop engineering for iOS mostly loop on **verification, not duration**. Every credible first-hand iOS or macOS account found keeps a human at plan approval and final review. Those accounts get their autonomy from headless build, test and simulator tools that let the agent check its own work in minutes. I found **no first-hand, measured report of an overnight Ralph or harness loop building or shipping an iOS app**. The only measured multi-hour autonomous runs are Anthropic's web-app harnesses ($125–$200 for 4–6 hours) and Huntley's compiler. Your goal is still achievable in a narrower form than "overnight, unattended, ships to the App Store". This project already has strong deterministic checks (65 tests, `tsc`, `deno check`, lint), and an Anthropic-style loop over `feature_list.json` can do multi-hour unattended runs on JS/TS logic, edge-function code and most UI screens. Three things stand in the way. **This Mac has no full Xcode**, so the agent cannot see or tap the app at all. **Production Supabase keys sit in the repo's `.env`**, and in auto mode reading `.env` and calling the matching API is allowed by default. And the app's core feature, the Vision cutout from the camera, **does not run in the iOS Simulator**. The plan at the end fixes the first two. The third stays a human checkpoint on a physical device.

## Every named loop is the same five parts

Ralph, Anthropic's harnesses and OpenAI's ExecPlans differ in packaging but share one skeleton. Each iteration feeds a fresh or compacted context the same instruction. Durable state lives on disk. Each iteration does one unit of work, and a machine check gates progress. A 2026 review that coined "loop engineering" lists the agreed building blocks as **triggers, machine-checkable stop conditions, persistent state files, verifier subagents, token budgets and human escalation points**. The same paper mined 36,710 repositories, found loops in only 217, and found **"no systematic evidence" for the benefits advocates claim** ([arXiv 2608.21884](https://arxiv.org/abs/2608.21884)). Treat what follows as practitioner and vendor experience, not established science.

The patterns differ mainly in who restarts the agent. Huntley's original Ralph is literally `while :; do cat PROMPT.md | claude-code ; done`. It keeps state in `specs/`, `fix_plan.md` and `AGENT.md`, does one item per loop, and relies on "backpressure" from tests and type checkers. Huntley scopes it to **greenfield work, about 90% complete, and says he would not use it on an existing codebase** ([ghuntley.com](https://ghuntley.com/ralph/)). That caveat matters, because Tabi Stickers is a mature codebase with 16 hard-won lessons in `skills.md`. The official Claude Code plugin implements the same loop inside one session through a Stop hook (`/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"`). Its **max iterations default to unlimited** ([ralph-loop README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)).

The harness kit you are adapting comes from Anthropic's November 2025 post. An initializer writes `init.sh`, a progress file and a `feature_list.json` in which every feature starts failing. Each later session reads git log and progress, **runs `init.sh` and a smoke test before new work**, implements one feature, verifies it, and flips only that feature's `passes` field. The post chose **JSON because models overwrite it less readily than Markdown** ([Anthropic, Nov 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The March 2026 follow-up added a planner and a separate Playwright-driven evaluator. It gives the best cost anchors available: a solo agent ran 20 minutes for $9 but left the core feature broken, while the full harness ran 6 hours for $200. On Opus 4.6, a digital audio workstation (DAW) build ran 3 h 50 m for **$124.70**, and the QA passes caught stubbed features the builder had claimed were done. That post also notes that out-of-the-box Claude "found issues, then talked itself into approving them", so **a separate, calibrated evaluator works better than asking the generator to be self-critical** ([Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)). Your kit's evaluator subagent is the right instinct. Its value depends entirely on what it can observe, and today it can observe nothing that runs on iOS.

The documented failure modes form a checklist your loop must defend against:

- Declaring victory early.
- Placeholder implementations.
- Duplicate code after a wrong "not implemented" search.
- Waking up to a broken tree ([ghuntley.com](https://ghuntley.com/ralph/)).
- Agents editing tests to pass. The EvilGenie benchmark caught explicit reward hacking by Claude Code and Codex ([arXiv 2511.21654](https://arxiv.org/abs/2511.21654v1)).

## iOS practitioners keep a human at the plan and buy speed with MCP

The Apple-platform reports describe fast, tool-verified, human-steered loops. Indragie Karunaratne shipped a roughly 20k-line macOS app with under 1,000 hand-written lines. He drove the app into bug states himself and pasted screenshots and logs back to Claude. He wrote that autonomous bug-fixing would need tests written in advance ([indragie.com](https://www.indragie.com/blog/i-shipped-a-macos-app-built-entirely-by-claude-code)). Jacob Bartlett's 2026 workflow uses XcodeBuildMCP with **human plan sign-off at about 10 minutes per change**. He calls verification "the #1 most important productivity unlock" and fully automatic orchestration "a little too rich for my blood" ([Jacob's Tech Tavern](https://blog.jacobstechtavern.com/p/agentic-ai-2026)). Blake Crosley got a full build-and-test health check down to about 90 seconds. He found that **judging visual correctness still needed a human or a separate vision model**, because layout bugs produce no build errors ([blakecrosley.com](https://blakecrosley.com/blog/xcode-mcp-claude-code)).

Expo's own direction is the closest match to your goal. Its agent docs support Claude Code directly. The Expo MCP server exposes EAS build logs, TestFlight crashes and feedback. On SDK 54 and later, the `expo-mcp` dev package adds local tools: `automation_take_screenshot`, `automation_tap` and `automation_find_view`, all addressable by testID, plus `collect_app_logs`. These local tools work **only on a macOS-hosted simulator, not physical devices** ([Expo MCP](https://docs.expo.dev/eas/ai/mcp/)). Expo's cloud "Simulators" product targets exactly the loop of feedback → agent fix → agent drives a build → evidence on the PR. It is a **limited-access preview, waitlisted, and not included in any plan** ([Expo Simulators](https://docs.expo.dev/preview/simulators/introduction.md)). So Expo's version of the dream exists, but you can't buy it yet, and you can build its local equivalent on your own Mac.

The tool landscape has shifted recently, which affects install commands. XcodeBuildMCP, now owned by Sentry, was **renamed MobileBuildMCP in v2.7.1 on 23 Sep 2026**. The package, binaries and config directory all changed, so earlier tutorials install a stale name ([GitHub releases](https://github.com/getsentry/XcodeBuildMCP/releases)). It bundles AXe for UI automation and adds `snapshot_ui`, `wait_for_ui` and `batch` for cheap accessibility-tree interaction ([GitHub releases](https://github.com/getsentry/XcodeBuildMCP/releases)). Maestro ships an official `maestro mcp`. Maestro's own recommended agent workflow is to explore with inline YAML, then save the working flow to `.maestro/` as a deterministic regression test that costs no tokens to re-run ([Maestro blog](https://maestro.dev/blog/mobile-ui-testing-with-coding-agents)). Maestro **requires Java 17+**, and this Mac has Java 1.8 ([Maestro install](https://docs.maestro.dev/maestro-cli/how-to-install-maestro-cli)). Every simulator-driving tool needs **full Xcode**. Command Line Tools have no `simctl`, which I confirmed locally. Xcode 27.x needs macOS 26.6+, which this Mac meets ([Apple](https://developer.apple.com/xcode/system-requirements/)).

| Verification layer | Tool | What it catches | Status on this Mac |
|---|---|---|---|
| Logic and types | `npm test`, `tsc`, `deno check`, `expo lint` | Scheduler, gloss, LLM adapter, type errors | Green today |
| Screen state | Expo MCP local tools, MobileBuildMCP `snapshot_ui` | Wrong screen, missing element, crash logs | Blocked: no Xcode |
| Regression flows | Maestro YAML in `.maestro/` | Sign-in, grading, sheet-dismiss regressions | Blocked: no Xcode, Java 8 |
| Visual quality | Screenshot plus separate evaluator | Layout, the "accurate but ugly" class | Blocked: no Xcode |
| Camera and cutout | Physical device only | Vision mask quality, capture | Human |

## The scan flow is the hard wall, and a cheap one

Two of the app's defining features **cannot be verified in the Simulator**, and no tool changes that. An Apple Frameworks Engineer stated that `VNGenerateForegroundInstanceMaskRequest` "is not supported on the CPU, so it will not run in the simulator" ([Apple Developer Forums](https://developer.apple.com/forums/thread/764948)). That evidence dates from 2024. One unverified anecdote suggests related Vision fixes landed in iOS 26.2, so test it once Xcode is installed rather than assume either way. The Simulator has **no camera** ([Expo iOS Simulator docs](https://docs.expo.dev/workflow/ios-simulator/)). Third-party injectors such as SimReel and SimulatorCamera feed images into `AVCaptureDevice`, but they need re-validating with every Xcode release ([SimReel](https://github.com/SolankiYogesh/simreel)). The routes that reach physical devices, mobile-mcp over USB and MobileBuildMCP device tools, all require code signing ([mobile-mcp](https://github.com/mobile-next/mobile-mcp); [MobileBuildMCP README](https://github.com/getsentry/XcodeBuildMCP)).

The wall doesn't have to block the rest of the scan flow. **Inference:** if the Swift module returns a fixture mask under `#if targetEnvironment(simulator)`, and photos are seeded with `xcrun simctl addmedia` ([notificare](https://notificare.com/blog/2020/05/22/Using-iOS-Simulator-with-the-Command-Line/)), the agent can drive the photo-picker path through cropping, the Gemini card, the study card and saving, with only the cutout itself faked. The cutout's gate thresholds already live in TypeScript (`lib/cutout.ts`, per skills.md #6). They can therefore be tested in the loop against stored fixture instance masks recorded once on a real device. Mask quality on real photos stays a human judgment on a physical phone, and that is the project's true irreducible checkpoint.

## Your Mac's real risks are the production keys, not the agent's competence

The safety model for unattended Claude Code is now well documented. Each layer leaves a gap, so the protection comes from stacking them:

- **Permission modes.** Auto mode routes actions through a classifier. It blocks production deploys, migrations and force pushes by default, but it explicitly **allows "reading `.env` and sending credentials to their matching API"**. After 3 consecutive or 20 total blocks it falls back to prompting ([Permission modes](https://code.claude.com/docs/en/permission-modes)).
- **Deny rules.** These **hold in every mode**, including bypass ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Bash patterns are fragile, though: `Bash(curl *)` won't match `sh -c 'curl …'` ([Permissions](https://code.claude.com/docs/en/permissions)).
- **Read denies.** These don't stop `grep -r` or a Node script from reading `.env` ([Permissions](https://code.claude.com/docs/en/permissions)).
- **The macOS Seatbelt sandbox.** It adds OS-enforced filesystem and network limits, with a network allowlist that starts empty. By default it still lets commands read most of the disk, **including `~/.ssh`**. It does not cover MCP servers or hooks ([Sandboxing](https://code.claude.com/docs/en/sandboxing)).

**Inference:** the only robust fix is that the production service-role key and the App Store Connect `.p8` are **not reachable** by the agent at all. Read denies and classifier judgment are not enough.

**Backend isolation** follows from that. Supabase recommends OrbStack for `supabase start` on macOS. It also offers an experimental **native runtime "meant for coding agent sandboxes or CI runners without a container engine"**, which suits this Mac, since it has no Docker. Branching is Pro-only at $0.01344 per branch-hour. The free plan allows **2 active projects**, which leaves room for a staging project that pauses after a week idle ([Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started); [Supabase pricing](https://supabase.com/pricing)). One wrinkle from this codebase: an edge function served locally still calls the real Gemini or Groq API. It needs its own capped dev key, and `npm run test:live` must stay out of the loop's gate.

**Cost** is the least certain number:

- **API prices.** Sonnet 5.5 is $2/$10 per million tokens and Opus 5.5 is $4/$20 ([Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)).
- **Practitioner Ralph runs.** These report about **$10/hour on 2025-era Sonnet** ([claudefa.st](https://claudefa.st/blog/guide/mechanics/ralph-wiggum-technique)). Re-scaled to today's prices that is roughly $5–7/hour, but that is an estimate, not a measurement.
- **Subscriptions.** Pro and Max share opaque 5-hour and weekly limits with claude.ai. Claude Code can wait for a reset with `autoContinueAtUsageLimit` ([Costs](https://code.claude.com/docs/en/costs); [Claude support](https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)).
- **Hard caps.** `claude -p --max-budget-usd` caps a run, and `--output-format stream-json` reports `total_cost_usd` and `permission_denied` events for logging ([Headless](https://code.claude.com/docs/en/headless)).

**EAS builds** stay outside the loop entirely:

- **Local builds don't use the quota.** Once Xcode is installed, `npx expo run:ios` and `eas build --local` compile on the Mac, and Expo's own skill calls local builds "free" ([Expo local development](https://docs.expo.dev/guides/local-app-development/); [expo-dev-client skill](https://raw.githubusercontent.com/expo/skills/main/plugins/expo/skills/expo-dev-client/SKILL.md)).
- **Cloud builds do.** The free plan's 15 iOS cloud builds are the scarce resource ([Expo pricing](https://expo.dev/pricing)).

| 7 | **Permissions in `~/.claude/settings.json`** (user scope, so the repo can't loosen them). Turn the sandbox on with `failIfUnavailable: true` and `allowUnsandboxedCommands: false`. Add `denyRead` for `~/.eas-keys`, `~/.ssh`, `~/secrets`, `~/.supabase`. The network allowlist covers the npm registry, `exp.host`, `127.0.0.1:8081` and `127.0.0.1:54321` (with `allowLocalBinding`), and **leaves off** `*.supabase.co`, `api.expo.dev` and the App Store hosts. | 8 | **Hooks.** Add a PreToolUse hook with `onFailure: "block"` that exits 2 on any command matching `eas`, `supabase (db\|functions\|link\|secrets)` or `git push`, to catch `sh -c` variants. Add a second PreToolUse hook denying Edit/Write to `scripts/test-*.mts`, `skills.md`, `.maestro/` and every field of `feature_list.json` except `passes`. Add an async `Stop`/`Notification` hook that `curl`s ntfy.sh with progress and any "build request" file. | Hook semantics sourced ([Hooks](https://code.claude.com/docs/en/hooks)); the test-protection pattern is practitioner ([DEV](https://dev.to/penloom_studio_829b7817d3/your-ai-agent-will-pass-any-test-its-allowed-to-edit-51fo)) |
| 9 | **`init.sh` gate**, cheapest check first: `npm run typecheck` → `npm run lint` → `npm test` → `npm run typecheck:functions` → (when deps changed) `npx expo-doctor` → (when `modules/` or `app.json` changed) `npx expo run:ios` → Maestro flows. Never run `test:live`. | Order is inference; tools sourced ([Expo tools](https://docs.expo.dev/develop/tools/)) |
| 10 | **`run-loop.sh`.** Each iteration runs `claude -p "$(cat PROMPT.md)" --permission-mode auto --permission-prompts none --max-budget-usd 5 --output-format stream-json --verbose \| tee logs/iter-$i.ndjson`, on a branch or worktree. Stop when there are no failing features, at the iteration cap, after N consecutive `permission_denied` events, or on `rate_limit`/`billing_error`. Do not use `--bare`, because the loop needs CLAUDE.md, the hooks and the MCP servers. | Flags sourced ([Headless](https://code.claude.com/docs/en/headless)); thresholds are inference |
| 11 | **Evaluator.** A separate subagent gets the feature's test steps and must observe through Expo MCP or MobileBuildMCP (accessibility tree first, screenshots for visual checks), with few-shot calibration against your own pass/fail judgments. It runs on a cheaper model so screenshots stay out of the builder's context. | Sourced pattern ([Anthropic, Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)); model choice inference ([Costs](https://code.claude.com/docs/en/costs)) |
| 12 | **Start small and measure.** Run 5 iterations attended, then one capped overnight run. Read `/usage` and the NDJSON costs before raising the caps. | Inference; no measured Expo loop cost exists |

**Which tasks the loop handles and which stay gated** (inference applied to this repo):

| Owner | Tasks |
|---|---|
| Loop | Features in `feature_list.json` whose test steps the gate or evaluator can observe: `lib/` logic, scheduler and gloss changes, prompt and schema changes in `_shared/` (checked with `deno check` and the `.mts` suites, never `test:live`), new migrations applied to **local** Supabase, UI screens reachable in the Simulator, Swift changes that compile locally, and Maestro flow maintenance. |
| Loop proposes, you approve | Writes a request file and notifies you: `supabase db push` and `functions deploy` to production, any `eas build` (per your standing rule), and `eas submit`. |
| You | Cutout quality on real photos, camera capture, push on device, visual sign-off of anything user-facing, App Store Connect, and any change to `skills.md` lessons or the tests themselves. |

## Conclusion

Huntley's "Ralph is a Bash loop" undersells where the leverage is. The loop script is about 20 lines, and the kit you have is already the right shape. What separates a loop that compounds from one that burns budget is the **observer**: the gate and evaluator can only certify what they can see. On this Mac today they can see types and logic but not one pixel of the app. Installing Xcode is therefore the single biggest autonomy unlock available, ahead of any prompt or harness refinement. Isolating the production backend is the precondition that makes running unattended defensible.

The honest ceiling is a loop that can run unattended for hours on everything except the scan and camera experience. It hands you a short queue of device checks, deploy requests and build requests, and leaves you as the reviewer rather than the operator. No public evidence yet shows anyone going further on iOS. If you instrument the first runs (cost per feature, evaluator agreement with your own verdicts, how often device checks overturn a simulator pass), you will have the measured report this field currently lacks.
